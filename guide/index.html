00 / WHY

결과보다 오래 남는 것은
과정입니다

2026년 7월부터 10월까지, 한 저장소에 남은 기록.

논문은 연구의 절반이고, 발표는 나머지 절반입니다. 그런데 둘 다 만드는 데는 연구보다 더 오랜 시간이 걸립니다. 저는 그 시간을 AI에게 통째로 맡기지 않고, 일을 나눠서 맡겼습니다.

2026년 가을, 저는 간암(HCC)과 혈관종을 B-mode 초음파에서 구분하는 연구를 대한가정의학회 추계학술대회에서 발표했습니다. 8분 발표, 2분 질의. 발표자료 13장, 대본 7분 35초, 큐카드 19장. 그 과정을 이 안내서에 담았습니다.

이 안내서는 결과를 자랑하려고 쓴 것이 아닙니다. 다음 사람이 같은 시간을 덜 쓰게 하려고 썼습니다. 제가 실제로 쓴 폴더 구조, 프롬프트, 검증 순서, 실패한 지점을 그대로 남겼습니다.

여러분의 연구는 제 연구와 다릅니다. 대부분 이미지가 아니라 국민건강영양조사(KNHANES) 원시자료를 씁니다. 그래서 이 안내서는 이미지 연구 사례를 예로 들되, 표 형식 데이터에 그대로 적용되는 방식으로 다시 썼습니다.

이 가이드가 약속하는 것

설치부터 첫 논문 초안, 학회 발표 큐카드까지 손을 잡고 한 단계씩 갑니다. AI를 잘 몰라도 됩니다. 명령어를 외울 필요도 없습니다. 복사해서 붙여넣을 문장을 준비했습니다.

약속하지 않는 것

AI가 통계를 대신 책임지지 않습니다. 인용을 지어내지 않는다는 보장도 없습니다. 마지막 판단과 서명은 사람이 합니다. 이 가이드는 그 판단을 빠르게 만드는 도구입니다.

“AI에게 논문을 써 달라고 하지 마세요. AI에게 연구를 검증하게 하세요. 순서가 반대입니다.” 이 가이드의 한 줄 원칙
01 / FIRST RUN

30분 안에 첫 성공을 만듭니다

목표: AI가 내 폴더의 파일 하나를 읽고, 한 문단을 고쳐 쓰게 한다.

설치는 세 단계입니다. ① OpenCode를 깐다 ② 이 저장소의 스킬을 복사한다 ③ 폴더를 열고 한 문장을 보낸다. 아래는 Windows 11 기준이며, macOS는 같은 순서에 명령만 다릅니다.

1

OpenCode를 설치합니다

터미널이 낯설면 Desktop 앱을 쓰세요. 화면은 일반 채팅 앱과 비슷합니다.

OpenCode는 채팅창이 아니라 내 컴퓨터의 폴더에서 직접 일하는 에이전트입니다. 설치 파일은 공식 배포 페이지에서 받습니다.

  • Windows 설치 파일 — opencode-desktop-win-x64.exe (ARM 노트북은 arm64)
  • macOS — Apple silicon · Intel
  • 공식 문서: opencode.ai/v2/docs

설치 후 앱을 열고 Connect(또는 설정 → Providers)에서 모델을 연결합니다. 처음이면 OpenCode Go 구독(월 10달러 수준)이 키 관리 없이 가장 간단합니다. DeepSeek 같은 API 키를 직접 넣어도 됩니다.

계정과 결제는 제가 대신 못 합니다

연구비 카드로 결제할지, 개인 카드로 할지는 소속 기관 규정을 먼저 확인하세요. 결제 정보는 절대 채팅창에 붙여넣지 않습니다.

2

이 저장소를 받고, 스킬을 복사합니다

Git을 몰라도 됩니다. GitHub에서 Code → Download ZIP을 누르면 끝입니다.

압축을 풀면 ai-research-copilot 폴더가 생깁니다. 그 안의 skills 폴더를 OpenCode가 읽는 위치로 복사합니다.

  • Windows: C:\Users\<내이름>\.config\opencode\skills
  • macOS·Linux: ~/.config/opencode/skills

탐색기에서 .config⁠가 안 보이면 폴더 주소창에 경로를 직접 입력하면 됩니다. 또는 저장소의 설치 스크립트를 실행하세요.

# Windows PowerShell — 저장소 폴더에서 실행
powershell -ExecutionPolicy Bypass -File .\install\install-windows.ps1

스크립트는 skills 폴더를 위 경로로 복사하고, 이미 있으면 덮어쓰기 전에 물어봅니다. 관리자 권한은 필요 없습니다.

스킬이 보이는지 확인하는 법

OpenCode를 다시 켠 뒤 대화창에 @academic-research-writing⁠을 입력했을 때 자동완성 목록에 뜨면 성공입니다. 안 뜨면 11장의 “스킬이 안 보일 때”를 보세요.

3

작업 폴더를 열고, 한 문장을 보냅니다

AI에게 “내 폴더를 보라”고 말로만 하지 말고, 폴더 자체를 열어 줍니다.

바탕화면에 my-paper 폴더를 만들고, 아무 문서나 하나 넣습니다. OpenCode Desktop에서 Open Folder로 그 폴더를 엽니다. 그러면 AI의 현재 위치가 그 폴더가 됩니다.

이 폴더에 있는 파일이 뭐가 있는지 알려줘.
아직 아무것도 고치지 말고, 읽기만 해.

AI가 파일 목록과 각 파일의 역할을 요약하면 첫 성공입니다. 이제 같은 폴더에서 아래를 보냅니다.

@academic-research-writing
이 폴더의 초록 초안을 읽고, 연구 질문(PICO)이 한 문장으로
명확히 드러나는지 검토해줘. 고치지는 말고, 문제 3개만 짚어줘.

답이 오면 “고쳐줘”가 아니라 “짚어줘”부터 했다는 점을 기억하세요. 이 순서가 이 가이드 전체의 리듬입니다.

여기서 막히면

① 앱이 안 열린다 → 재부팅 후 다시 실행. ② 모델 연결이 안 된다 → 결제·키 문제이므로 /connect 화면을 다시 확인. ③ 스킬이 안 보인다 → 복사 경로의 철자 확인(.config/opencode/skills/<스킬이름>/SKILL.md). ④ 그래도 안 되면 11장 FAQ로.

02 / MENTAL MODEL

챗봇은 말하고,
에이전트는 파일을 고칩니다

이 차이를 모르면 첫 주에 반드시 사고가 납니다.

ChatGPT 창에 논문을 붙여넣고 “다듬어 줘”라고 하는 것과, OpenCode에게 “이 폴더의 원고를 읽고 표 2와 본문 숫자가 맞는지 확인해”라고 하는 것은 다른 일입니다.

에이전트가 하는 네 가지

  • 읽기 — 폴더의 원고·CSV·코드·PDF를 읽습니다.
  • 쓰기 — 새 파일을 만들거나 기존 파일을 고칩니다.
  • 실행 — Python·R 코드를 돌려 표와 그림을 만듭니다.
  • 검색 — 웹과 논문 데이터베이스에서 근거를 찾습니다.

이 네 가지를 하려면 경계가 필요합니다. 그래서 OpenCode는 폴더를 열게 하고, 위험한 작업은 허가를 받게 합니다. “파일을 지워도 됩니까?”라고 물으면 대부분은 아니오입니다.

기억해야 할 세 문장

01

폴더 밖은 건드리지 않습니다

작업 폴더를 논문 하나로 좁히면 사고 범위도 좁아집니다.

02

대화는 사라지고 파일은 남습니다

중요한 결정은 채팅이 아니라 notes/decision.md에 적게 하세요.

03

한 번에 한 가지

“논문 전체를 써줘”는 실패합니다. “표 1의 변수 정의를 맞춰줘”가 성공합니다.

03 / WORKSPACE

AI가 읽고 쓸 책상을
먼저 만듭니다

폴더 이름은 영어, 내용은 한국어. 이 조합이 가장 덜 깨집니다.

논문 한 편 = 폴더 하나. 이 원칙만 지키면 나중에 파일을 찾느라 반나절을 쓰지 않습니다. 아래 구조를 그대로 만들어도 되고, 필요한 것만 골라도 됩니다.

# my-paper/ — 논문 한 편의 책상
my-paper/
├─ 00_admin/          IRB, 저널 규정, 이해상충
├─ 01_data/
│  ├─ raw/            원본 — 절대 수정하지 않음
│  ├─ derived/        코드가 만든 분석용 데이터
│  └─ codebook/       변수 설명서, 설문지
├─ 02_analysis/
│  ├─ 01_clean.R      정제·결측·가중치
│  ├─ 02_table1.R     표 1
│  ├─ 03_models.R     주 분석
│  └─ logs/           실행 로그
├─ 03_output/
│  ├─ tables/         CSV + docx
│  └─ figures/        PNG + SVG
├─ 04_manuscript/
│  ├─ manuscript.md   원고 단일 원본
│  ├─ references.bib
│  └─ submission/     투고 세트
├─ 05_talk/
│  ├─ outline.md      제목 = 주장
│  ├─ deck/           HTML · PDF · PPTX
│  ├─ script.md       대본
│  └─ cuecards/       인쇄용 PDF
└─ notes/
   ├─ decision.md     왜 이렇게 했는지
   └─ todo.md

왜 이렇게 나누나

raw는 성역입니다. 원본 데이터를 고치면 재현이 불가능해집니다. AI에게도 “raw는 읽기만”이라고 명시하세요. OpenCode는 파일 권한을 물어보지만, 사람이 규칙을 먼저 정하는 편이 안전합니다.

derived는 코드가 만듭니다. 손으로 만든 엑셀은 6개월 뒤에 설명할 수 없습니다. 정제 단계부터 코드로 남기면, 심사자가 “이 변수는 어떻게 정의했나요?”라고 물을 때 파일 하나를 보여주면 됩니다.

manuscript는 한 파일입니다. manuscript_v3_final_final.docx⁠가 다섯 개가 되는 순간 끝입니다. 마크다운 한 파일을 원본으로 두고, 제출용 docx는 매번 새로 굽습니다.

notes/decision.md가 가장 값어치 있습니다. “가중치는 연도별로 나눴다”, “이 변수는 2019년부터 문항이 바뀌어 통합하지 않았다” 같은 판단을 적어 두면, 3개월 뒤의 나와 심사자가 같은 문서를 봅니다.

첫 폴더를 만드는 프롬프트

빈 폴더를 열고 아래를 보내면 위 구조를 만들어 줍니다. 만든 뒤에는 각 폴더에 무엇을 넣을지를 README.md에 적게 하세요.

지금 폴더에 논문 한 편을 위한 작업 구조를 만들어줘.
위 구조를 참고하되, 파일은 만들지 말고 폴더와 README.md만.
README.md에는 각 폴더의 역할과 "raw는 수정 금지" 규칙을 적어줘.
만들기 전에 어떤 폴더를 만들지 먼저 보여줘.

파일 이름 규칙 — 나중의 나를 위한 배려

같은 폴더를 6개월 뒤에 열어도 이해되는 이름

04 / SKILLS

일곱 개의 스킬,
일곱 가지 역할

스킬은 “프롬프트 모음”이 아니라 일하는 절차서입니다.

스킬은 AI에게 주는 업무 매뉴얼입니다. 그냥 “논문 써줘”라고 하면 평범한 답이 오지만, @academic-research-writing⁠을 붙이면 근거 장부를 만들고, 인용을 검증하고, 숫자를 표로 보내는 절차를 따릅니다.

스킬 목록

@academic-research-writing

논문·문헌고찰

연구 질문을 계약서로 만들고, 근거 장부(ledger)를 쌓고, IMRaD 원고를 씁니다. 인용은 “존재 확인”과 “주장 지지 확인”을 따로 합니다.

쓸 때: 원고 초안, 문헌고찰, 체계적 고찰, 투고용 리포트

@deep-research

조사·팩트체크

질문을 쪼개 넓게 찾고 좁히며, 모든 주장에 출처를 붙입니다. “최신 동향” “비교해줘” “사실 확인”의 기본 경로입니다.

쓸 때: 배경 조사, 가이드라인 비교, 통계 수치 확인

@paper-review

제출 전 자체 심사

이미 쓴 원고·표·그림·발표자료를 심사자 관점에서 감사합니다. AI 티, 숫자 나열, 인용·표·그림 번호, 덱 커버리지를 봅니다.

쓸 때: 투고 1주 전, 발표 3일 전

@design-craft

보이는 것의 설계

보고서·포스터·슬라이드의 색·타이포·여백·밀도를 정하고, 검사 스크립트로 넘침과 대비를 확인합니다. 표면마다 테마를 새로 뽑습니다.

쓸 때: PDF·HTML·포스터를 사람에게 건넬 때

@deck-craft

발표자료

16:9 고정, 한 장에 한 아이디어, 제목은 주장. 도표는 이미지 생성이 아니라 SVG로 그립니다. HTML·PPTX·PDF를 함께 만듭니다.

쓸 때: 학회·교원 연수·IR 발표

@script-to-cuecards

06 / KNHANES

국민건강영양조사는
설계가 절반입니다

AI가 가장 자주 틀리는 지점이 바로 여기입니다.

국민건강영양조사는 “전국 대표성”을 위해 층화·집락·가중치를 쓰는 복합표본조사입니다. 이 설계를 빼고 mean()⁠을 돌리면 숫자는 나오지만, 그 숫자는 한국 국민의 값이 아닙니다.

왜 가중치를 써야 하나

조사에 참여한 사람이 국민 전체를 대표하도록 각 참여자에게 가중치를 줍니다. 가중치를 빼면 젊은 층이 과대표되고, 유병률이 실제와 달라집니다. 층·집락을 빼면 표준오차가 과소평가되어 p값이 실제보다 작아집니다. 즉, 없는 유의성이 생깁니다.

KNHANES 원시자료에는 보통 층(kstrata), 집락(psu), 가중치(wt_*)가 들어 있습니다. 정확한 변수명은 연도·파일마다 다르므로 반드시 코드북에서 확인해야 합니다.

AI에게 반드시 말할 한 문장

“이 분석은 복합표본설계입니다. 층·집락·가중치를 반영하고, 변수명은 코드북에서 확인한 뒤 주석에 적으세요. 가중치를 빼면 결과를 폐기하겠습니다.”

이 문장을 매 분석 프롬프트에 붙이세요. 한 번 말하고 잊으면, 세 번째 스크립트에서 조용히 빠집니다.

코드의 모양 — R과 Stata

아래는 구조를 보여 주는 예시입니다. 변수명은 여러분의 연도·파일 코드북에서 확인한 이름으로 바꿔야 합니다. 그대로 복사해 실행하면 안 됩니다.

2024년 기준 — 어떤 가중치를 쓰나

2024년(제9기 3차년도) 코드북 p.94에서 확인한 이름입니다. 2024년에는 wt_exam이 없습니다. 2010년부터 건강설문·검진이 wt_itvex로 통합되었습니다.

가장 흔한 오류 — 없는 변수

wt_exam, wt_ex, wt_itv는 2024년 기본 가중치가 아닙니다. 코드북에 없는 이름을 쓰면 R은 “object not found”로 멈추지만, 다른 해 파일과 섞으면 조용히 잘못된 결과가 나옵니다.

변수설명쓰는 경우
wt_hs가구조사 가중치가구 단위 분석(소득·가구원수)
wt_itvex건강설문–검진조사BMI·혈압·혈액검사 + 설문 (가장 흔함)
wt_ntr영양조사영양 변수만 (+ 연령·성별)
wt_tot건강설문–검진 + 영양검진 변수와 영양 변수를 한 모형에
wt_oe · wt_oent구강 · 구강+영양구강검사 분석
wt_bia · wt_biant체성분 · 체성분+영양2022년만
wt_pft · wt_pfnt폐기능 · 폐기능+영양2024년만

선택 규칙은 “결과 변수”가 아니라 “모형에 함께 넣는 모든 변수”입니다. 예를 들어 BMI(검진)와 고혈압(검진)은 wt_itvex, BMI와 에너지 섭취량(영양)을 함께 넣으면 wt_tot입니다. 가구소득만 보면 wt_hs입니다.

더 자세한 정리

가중치 10종의 전체 표, R·Stata 코드, 하위집단 분석, 2022–2024 통합(연 192개 조사구 → 1/3), 실수 8가지, 논문 방법 문장은 knhanes-weights.md · PDF에 따로 정리했습니다. 이 장은 요약입니다.

연도를 합칠 때 — 가장 위험한 부분

서로 다른 연도의 원시자료를 단순히 rbind하고 한 번에 분석하면 가중치가 틀어집니다. 제9기는 연 192개 조사구, 3년 576개이므로 연도별 가중치에 192/576 = 1/3을 곱한 통합가중치를 씁니다(지침서 p.30의 일반 원칙). 기수 간 통합은 1/3이 아니라 조사기간 비율입니다. 확신이 없으면 통계 담당자에게 확인하고, 그 결정을 notes/decision.md에 남기세요. AI에게 “알아서 해줘”라고 하면 안 됩니다.

07.5 / REVIEW

심사 발표를 앞두고,
질문을 먼저 설계합니다

좋은 연구를 설명하는 것과 심사에서 좋은 평가를 받는 것은 다른 기술입니다.

심사위원이 자주 묻는 질문은 통계가 아니었습니다. IRB를 통과했는가, 이 연구를 계속할 것인가, 임상에서 어디에 쓸 수 있는가. 세 질문 모두 “비판”이 아니라 다음 단계를 묻는 질문이었습니다.

심사위원의 세 가지 질문

질문 1

“IRB는 통과했나요?”

심사위원은 연구의 윤리적 근거를 확인합니다. 답이 흐리면 나머지 점수도 흔들립니다.

질문 2

“이거 계속 연구할 건가요?”

일회성 발표인지, 연구 프로그램인지 봅니다. 다음 질문이 있는 사람이 높게 평가받습니다.

질문 3

“임상에서 어디에 쓰나요?”

성능표가 아니라 진료 흐름의 어느 지점을 바꾸는지 묻습니다.

세 질문에 대한 답변 틀

1

IRB — “통과했습니다”가 아니라 “이 근거로 면제/승인받았습니다”

준비물: 승인번호, 승인일, 기관명, 연구 유형(전향/후향), 동의 면제 사유. 공개 데이터셋이면 심의면제 확인서를 지참합니다.

30초 답변 예시

“본 연구는 OO병원 IRB에서 승인번호 OOOO로 승인받았습니다. 후향적 검사 데이터를 익명화해 사용했고, 환자 동의는 면제되었습니다. 공개 데이터셋 부분은 국가 공개 자료로 기관 심의면제 확인을 받았습니다.”

말하지 말아야 할 것

“IRB가 필요 없는 연구였어요.” 필요 없다고 단정하기보다 어떤 근거로 면제받았는지를 말합니다. 기관마다 요구가 다르므로 발표 전에 확인서를 출력해 가방에 넣어 두세요.

2

계속 연구 — “네”보다 “이렇게 하겠습니다”

구체적인 1년 계획을 2~3문장으로 준비합니다. 하고 싶은 것만 말하면 산만해 보이고, 하지 않을 것을 함께 말하면 신뢰가 생깁니다.

30초 답변 예시

“다음 단계는 외부 병원 코호트로 검증하는 것입니다. 올해는 전향적으로 200예를 모을 계획이고, 다기관으로 확장하기 전에 이 기관에서 재현성을 먼저 확인하겠습니다. 상용화나 규제 승인은 아직 계획에 없습니다.”

3

임상 응용 — “정확도”가 아니라 “워크플로의 어느 칸”

“판독을 대체한다”가 아니라 “판독 전에 위험을 표시한다”, “검진에서 재검 대상자를 좁힌다”, “교육에서 전형과 비전형을 보여 준다”처럼 한 칸을 지정합니다.

30초 답변 예시

“저는 이 지표를 판독 대체가 아니라 보조로 봅니다. 초음파 판독 전에 ‘전형 HCC에서 얼마나 먼가’를 보여 주면, 비전형 증례를 놓치지 않게 도울 수 있습니다. 다만 전향적 검증 전에는 임상 결정에 쓰지 말아야 한다고 생각합니다.”

어떤 데이터로 하는 연구가 설득력이 있나

최근 발표 심사에서 좋은 평가를 받은 연구는 대체로 두 갈래였습니다. 국민건강영양조사 2차 분석만으로는 독창성을 보이기 어렵습니다.

갈래 A · 원내 코호트

내 기관에서 직접 쌓은 데이터

예: 검진센터에서 구축한 H. pylori 위염 후향 코호트. 데이터를 만든 것 자체가 기여입니다. 검진센터·외래·내시경실 데이터를 연구 가능한 형태로 정리하는 일이 핵심입니다.

갈래 B · 공개 데이터셋

재현 가능한 벤치마크

예: 제 연구(SMC-LUD). 누구나 같은 데이터로 재현할 수 있어 방법론의 기여가 분명합니다. 대신 “왜 이 데이터여야 하는가”와 “외부 타당도”를 반드시 답해야 합니다.

데이터 전략별 장단점 — 발표 기획 단계에서 정합니다
데이터강점약점설득 전략
국민건강영양조사전국 대표성, 무료, 표본 큼2차 분석이라 독창성 약함, 인과 추론 제한, 변수 제한정책·인구집단 질문 + 연도 추세 + 다른 데이터와 연결. “처음 규명한 인구집단”을 전면에.
원내 후향 코호트우리 기관만의 데이터, 임상 맥락 강함선택 편향, 결측, IRB·개인정보 부담코호트 구축 과정과 정의를 방법의 기여로. 임상 워크플로 변화를 보여 줌.
공개 데이터셋재현 가능, 벤치마크, 빠른 시작독창성 경쟁, 외부 타당도 의문방법론 기여 + 외부 검증 계획 + “이 데이터의 한계”를 먼저 말함.
국민건강영양조사로 승부한다면

① “유병률 조사”에서 멈추지 말고 정책이 바뀌어야 하는 이유까지 간다. ② 한 해가 아니라 여러 해의 추세를 본다. ③ 가능하면 원내 자료나 다른 공개 자료와 연결해 “검증”을 붙인다. ④ 발표 제목에 대상·기간·핵심 발견을 넣는다. “한국 성인의 OO 추이: 2010–2023”처럼.

08 / CONVERSATION

대화 규칙 열둘 —
hand-to-hand로 일하는 법

프롬프트 기술보다 일을 나누는 순서가 중요합니다.

AI와 일할 때 실패하는 이유는 대개 모델 성능이 아니라 한 번에 너무 많이 시키는 것입니다. 아래 열두 규칙은 제가 네 달 동안 지킨 것이고, 어기면 반드시 되돌아왔습니다.

1. 폴더를 열고 시작한다

“내 컴퓨터에 있는 논문”이라고 말하지 않습니다. 폴더를 열어 현재 위치를 맞춥니다. AI가 엉뚱한 파일을 읽는 사고의 90%가 여기서 납니다.

2. 계획을 먼저 받는다

“고쳐줘” 전에 “어떻게 고칠지 먼저 보여줘”라고 합니다. 계획이 틀렸으면 파일을 건드리기 전에 멈출 수 있습니다.

먼저 계획만 보여줘. 파일은 아직 고치지 마.
계획을 읽고 내가 승인하면 그때 실행해.

3. 한 번에 하나

“표 1, 표 2, 그림 3, 원고를 한 번에”는 실패합니다. 한 항목을 끝내고 결과를 확인한 뒤 다음으로 갑니다. 대화가 길어지는 것보다 짧은 왕복이 빠릅니다.

4. 결정은 파일로 남긴다

채팅은 사라집니다. “가중치는 연도별로 나눴다” 같은 결정은 notes/decision.md에 날짜와 함께 적게 합니다. 3개월 뒤의 내가 읽을 수 있어야 합니다.

5. 숫자는 표로 보낸다

문장에 숫자를 넣으면 AI가 표와 다른 숫자를 써도 눈치채기 어렵습니다. 문장 하나에 숫자 하나, 나머지는 “표 2를 보시면”으로 넘깁니다.

6. 출처 없는 문장은 쓰지 않는다

서론·고찰의 모든 근거 문장에는 인용이 붙어야 합니다. AI가 “잘 알려져 있다”고 하면 “어디에?”라고 묻습니다. 답이 없으면 그 문장은 삭제합니다.

7. “모른다”고 말하게 한다

프롬프트에 이 문장을 넣으세요: “확실하지 않으면 ‘확인 필요’라고 적고 추측하지 마.” AI는 빈칸을 채우려는 습성이 있습니다. 빈칸을 남기는 것이 실력입니다.

8. 되돌릴 수 있게 만든다

큰 수정 전에는 폴더를 복사하거나 git 커밋을 합니다. “이전 버전으로 돌려줘”는 파일이 남아 있을 때만 가능합니다.

지금 상태를 git에 커밋해줘. 메시지는 "before table revision".
그다음 수정을 시작해.

9. 내 말투로 고친다

AI 문장은 매끄럽지만 나와 닮지 않았습니다. 소리 내어 읽고 내가 실제로 말할 문장으로 바꿉니다. 발표 대본은 특히 그렇습니다.

10. 검증 질문을 던진다

“이 숫자의 출처 파일이 뭐야?”, “이 표의 n은 어디서 왔어?”, “이 인용이 그 주장을 실제로 지지해?” 답을 파일로 보여 주지 못하면 믿지 않습니다.

11. 길어지면 새로 시작한다

대화가 2시간을 넘으면 앞 내용을 잊습니다. “지금까지 결정·경로·다음 할 일을 handoff.md로 정리해줘”라고 한 뒤 새 세션을 시작합니다.

12. AI는 저자가 아니다

AI 사용은 방법이나 감사의 말에 공개하고, 저자 자격은 없습니다. 최종 책임은 사람에게 있습니다. 저널마다 규정이 다르니 투고 전에 확인합니다.

09 / SAFETY

믿지 않을 것은
믿지 않기

AI는 빈칸을 채우고, 사람은 빈칸을 남깁니다.

AI가 만든 원고에서 가장 위험한 것은 문장이 아니라 숫자와 인용입니다. 문장은 읽으면 이상한 티가 나지만, 숫자와 DOI는 그럴듯해서 그냥 지나갑니다.

환각 — 세 가지 얼굴

  • 없는 논문 — 저자·연도·DOI가 모두 그럴듯하지만 존재하지 않습니다.
  • 맞는 논문, 틀린 주장 — 논문은 있지만 내 주장을 지지하지 않습니다.
  • 그럴듯한 숫자 — 표에 없는 값이 본문에 등장합니다.

대응은 하나입니다. 원문·원자료로 돌아가기. “DOI 확인”은 “주장 지지 확인”이 아닙니다.

인용 검증 3종 세트

이 원고의 참고문헌을 하나씩 검증해줘.
각 항목에 대해:
1. 논문이 실제로 존재하는가 (DOI/PMID로 확인)
2. 내가 인용한 문장이 그 논문의 어느 부분에서 지지되는가 (쪽·표)
3. 접근 수준 (full_text / abstract / metadata_only)
셋 중 하나라도 확인 못 하면 "확인 불가"로 표시하고,
그 인용을 쓰지 말라고 표시해.

개인정보 — 절대 규칙

  • 환자 이름·등록번호·생년월일·연락처·주소는 어떤 채팅에도 넣지 않습니다.
  • 원내 데이터는 기관 정책을 먼저 확인합니다. 외부 모델 제공자로 전송될 수 있습니다.
  • 국민건강영양조사 원시자료는 공개 자료지만, 재배포·업로드는 이용 약관을 확인합니다.
  • 스크린샷에는 종종 환자 정보가 함께 찍힙니다. 올리기 전에 잘라냅니다.

AI 사용 공개

저널·학회마다 문구가 다릅니다. 보통 “English language editing”인지 “analysis support”인지 구분해 적습니다. AI는 저자가 될 수 없고, 분석을 했다면 방법에 적습니다. 제출 전에 목표 저널의 최신 지침을 확인하세요.

통계 — AI에게 맡기면 안 되는 것

  • 표본 크기·검정력 계산의 가정
  • 복합표본 가중치·층·집락 처리
  • 다중비교 보정, 결측 처리, 민감도 분석
  • “유의하다”의 해석

AI는 코드를 빨리 쓰지만, 설계의 타당성은 검증하지 못합니다. 통계 담당자와 한 번 더 확인하세요.

제가 실제로 겪은 일

리뷰 대응 중 표와 본문의 숫자가 어긋난 적이 있습니다. 원인은 AI가 아니라 제가 표를 마지막에 고쳤기 때문이었습니다. 그래서 지금은 원고를 고친 뒤 반드시 “표·그림·초록·본문의 숫자를 서로 대조하는 표”를 만들게 합니다. 이 표 하나가 리뷰어의 지적을 여러 개 막습니다.

숫자 대조표 프롬프트

아래를 원고 마지막에 붙이면, 제출 전에 숫자 불일치를 잡을 수 있습니다.

원고 본문·초록·표·그림 캡션에 등장하는 모든 숫자를 추출해
"숫자 / 나오는 위치 / 표의 값 / 일치 여부" 표로 만들어줘.
일치하지 않는 항목은 HIGH로 표시하고, 어느 쪽이 맞는지 원자료로 확인해.
확인 못 하면 "원자료 확인 필요"라고 적어.

자주 막히는 곳 — FAQ

스킬이 자동완성에 안 보입니다

경로를 확인하세요: ~/.config/opencode/skills/<스킬이름>/SKILL.md. 폴더가 한 겹 더 들어가 있으면(skills/design-craft/design-craft/SKILL.md) 인식되지 않습니다. OpenCode를 완전히 종료했다가 다시 켜세요.

AI가 파일을 못 찾습니다

현재 폴더가 맞는지 확인하세요. “파일이 없다”고 하면 “폴더 목록을 보여줘”라고 먼저 물어보세요. 그래도 없으면 경로를 직접 알려 주세요.

한국어가 깨지거나 영어로 답합니다

한국어로 쓰라고 명시하세요: “본문은 한국어, 표 머리글도 한국어. 고유명사만 영어.” 폰트 문제로 PDF가 깨지면 HTML을 PDF로 인쇄할 때 한글 폰트가 설치된 PC에서 하세요.

표가 Word에서 깨집니다

docx는 환경에 따라 레이아웃이 달라집니다. 제출 직전에는 Word에서 직접 열어 표 폭·페이지 나눔을 확인하세요. 이 확인은 AI가 대신할 수 없습니다.

비용이 걱정됩니다

긴 세션은 비쌉니다. ① 한 세션에서 한 가지 일만 ② 파일 전체를 붙이지 말고 필요한 부분만 ③ 2시간마다 handoff 후 새 세션. 이 세 가지로 비용이 크게 줄어듭니다.

발표장에서 파일이 안 열립니다

HTML은 발표 PC의 브라우저·폰트에 따라 달라집니다. PDF를 함께 준비하고, PDF로 발표하세요. 동영상·애니메이션이 있으면 MP4로 따로 저장합니다.
