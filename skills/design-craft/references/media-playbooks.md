# 매체별 플레이북

같은 디자인 원칙을 매체마다 다른 규격으로 적용한다. **공통 3문서 파이프라인은 유지**하고, 캔버스·
타이포 스케일·검증 방법만 바꾼다.

매체 판별을 먼저 한다. 애매하면 사용자에게 한 번 묻는다("홈페이지인가, 발표자료인가?"). 매체를
잘못 잡으면 검증 방법이 전부 어긋난다.

## 1. 홈페이지 · 랜딩페이지

| 항목 | 값 |
|---|---|
| 캔버스 | 1440 데스크톱 / 375 모바일 기준, 컨테이너 1200–1280px |
| 섹션 | 히어로 → (브릿지: 브랜드 메시지·무드) → 그리드/기능 → 증거(수치·후기) → CTA → 푸터 |
| 타이포 | 히어로 `clamp(2.5rem, 6vw, 5.5rem)`, 본문 17–18px, measure 45–75자 |
| 검증 | `shot.sh --width 1440 --full` + `--width 375`, `design-lint.py` |

주의:

- 히어로에서 바로 그리드로 넘어가면 스토리텔링이 끊긴다. **브릿지 섹션**을 반드시 넣는다
  (브랜드 메시지, 무드 파노라마, Horizontal Scroll 등).
- 브릿지는 "가로 스크롤 + 하단 타임라인" 같은 강한 패턴 하나를 쓴다.
- 스크롤 길이가 길어지므로 섹션별 밀도를 바꾼다(꽉 참 → 텅 빔).
- 성능: 히어로 이미지 1컷만 LCP 로 잡고 나머지는 lazy. 폰트는 서브셋 + `font-display: swap`.

- **좌우 여백 필수**: `--pad-x: clamp(20px, 5vw, 64px)` + `--maxw ≤ 1080px`.
  `.wrap` 에 `padding: X 0 Y` 축약형을 쓰면 좌우가 0이 되어 폰에서 본문이 화면 끝에 붙는다(SKILL.md 의 좌우 여백 절).
  표·이미지도 같은 컨테이너를 써서 기준선을 맞춘다. 375px 스크린샷으로 반드시 확인한다.

## 2. 웹앱 · SaaS 제품 화면

| 항목 | 값 |
|---|---|
| 캔버스 | 앱 셸(사이드바 240–280px, 헤더 56–64px), 콘텐츠 그리드 4/8/12 |
| 밀도 | 데이터 도구는 조밀하게(행 32–40px), 마케팅 화면은 넓게 |
| 검증 | 상태 4종(빈/로딩/에러/권한없음) 스크린샷 각각 |

주의:

- **상태 정의가 UX 문서에 없으면 앱은 미완성이다.** 정적 쇼케이스와 달리 로딩 스켈레톤, 인라인
  검증, 토스트, 빈 상태를 반드시 설계한다.
- 밀도가 높은 표는 zebra 대신 1px 행 구분 + 숫자 정렬(tabular-nums)을 쓴다.
- 색은 상태색(success/warn/danger)과 악센트를 분리한다 — 악센트로 경고를 표시하지 않는다.
- 키보드 경로: Tab 순서, ⌘K 팔레트, `:focus-visible`.

## 3. 대시보드 · 데이터 시각화

| 항목 | 값 |
|---|---|
| 캔버스 | 12컬럼 그리드, 카드 최소 폭 280px, 차트 높이 200–320px |
| 타입 | 숫자 크게(28–40px, tabular), 라벨 작게(11–12px, 대문자+자간) |
| 검증 | 축·단위·기간이 화면에 보이는가, 색만으로 구분하지 않는가 |

주의:

- 숫자 하나가 주인공이면 KPI 타일로 키우고, 나머지는 보조로 낮춘다. 모든 카드를 같은 크기로
  만들면 읽는 순서가 사라진다.
- 차트 색은 순차(sequential) 팔레트를 쓰고, 범주형은 최대 5색 + 패턴/모양 보조.
- 빈/오류 데이터 상태를 반드시 그린다.

## 4. 카드뉴스

| 항목 | 값 |
|---|---|
| 캔버스 | 인스타 4:5 = **1080×1350** (권장), 정방 1080×1080, 스토리 1080×1920 |
| 세이프존 | 상하좌우 96–120px 안쪽에만 핵심 요소 |
| 장수 | 5–10장. 1장 = 1메시지 |
| 타이포 | 제목 72–110px, 본문 40–52px, 캡션 32–36px. 최소 32px 미만 금지 |
| 검증 | 각 장을 PNG 로 렌더 → 폰 크기에서 텍스트가 읽히는지 |

제작 절차:

1. 카드별 메시지를 **텍스트로 먼저** 확정한다(장수, 각 장 제목/본문/출처).
2. 표지 → 문제 → 근거/데이터 → 방법 → 결론 → CTA 순으로 흐름을 만든다.
3. HTML/CSS 로 카드 템플릿을 만들고, 데이터 배열을 돌려 각 장을 렌더한다.
4. `shot.sh` 로 장당 PNG 를 뽑는다(`--width 1080 --height 1350`).
5. `kimaki upload-to-discord` 로 이미지를 사용자에게 보낸다.

주의:

- 한 장에 문장 3개를 넘기지 않는다. 넘치면 장을 늘린다.
- 표지에 숫자/질문 하나만 크게 — 스크롤을 멈추게 하는 건 그 한 줄이다.
- 배경은 브랜드 토큰 색으로 통일하고, 장마다 레이아웃 변주(좌/우 정렬 교차)로 리듬을 만든다.
- 출처가 필요한 주제(의학·통계)면 각 장 하단에 출처를 작게 넣는다.

## 5. 발표자료 · 슬라이드

| 항목 | 값 |
|---|---|
| 캔버스 | 16:9 = **1920×1080** (또는 1280×720) |
| 여백 | 상하좌우 최소 80px(1920 기준), 제목존 상단 120px |
| 타이포 | 슬라이드 제목 48–72px, 본문 **28pt(≈37px) 이상**, 각주 18–20px |
| 밀도 | 1 슬라이드 = 1 주장. 불릿 최대 4개, 각 2줄 이내 |
| 검증 | 발표장 뒤에서 읽히는가(최소 24pt), 슬라이드당 정보량 |

절차:

1. 슬라이드 제목만 나열한 **아웃라인**을 먼저 확정한다(각 제목이 곧 주장이어야 한다).
2. 슬라이드 유형을 정한다: 표지 / 주장+근거 / 도표 / 인용 / 비교 / 결론 / Q&A.
3. HTML 슬라이드(각 슬라이드 = `section`, CSS `@page`/`aspect-ratio`)로 렌더하고
   `shot.sh` 로 슬라이드별 PNG 를 뽑는다.
4. PPTX 가 필요하면 HTML→이미지 슬라이드를 배경으로 넣거나 사용자에게 형식을 확인한다.

주의:

- "개요(Agenda)" 슬라이드에 목차만 넣는 건 정보가 아니다 — 각 항목에 결론을 붙여라.
- 도표는 슬라이드당 1개. 축·단위·기간을 슬라이드 안에 쓴다.
- 색은 3색 이내(배경·텍스트·악센트), 강조는 악센트 하나로만.
- 마지막 슬라이드는 "감사합니다"가 아니라 결론/요청이다.

## 6. 리포트 · 문서 PDF

| 항목 | 값 |
|---|---|
| 캔버스 | A4 (210×297mm), 여백 상하 20mm 좌우 18mm |
| 타입 | 본문 10.5–11pt, 행간 1.55, 제목 18–24pt |
| 표 | 머리행만 배경, 세로줄 없음, 숫자는 우측 정렬 + tabular |
| 검증 | 페이지 나눔, 고아 줄, 표 잘림, 목차 링크 |

절차 (이 머신의 실제 도구):

- Markdown 으로 쓰고 렌더링된 PDF 를 얻는다: `~/.local/bin/md-view <file.md> --pdf`
  (pandoc.exe + headless Chrome 체인, pandoc 은 stdin/stdout 으로만 넘긴다).
- 렌더링된 링크만 필요하면 `md-view <file.md>` → GitHub 렌더 gist URL.
- 환자정보·PHI·기밀은 gist 에 올리지 않는다 → PDF 또는 본문 붙여넣기만.
- Discord 에서는 markdown 표가 렌더되지 않는다 → 불릿/코드블록 정렬표/md-view PDF 중 하나.

주의:

- 문서 디자인에서 가장 큰 품질 차이는 **여백과 위계**다. 색을 늘리지 않는다.
- 표는 페이지를 넘길 때 머리행을 반복한다.
- 각주와 출처를 일관된 형식으로 쓴다.
- 인쇄 검정은 순수 `#000` 이 아니라 `#111` 계열이 더 부드럽다.

## 7. 매체 공통 체크

- 캔버스 비율과 최소 타이포를 **먼저** 정하고 시작한다.
- 세이프존(모바일 노치·크롭) 안에 핵심을 둔다.
- 렌더 결과를 이미지로 뽑아 실제 크기에서 확인한다 — 코드로 "될 것 같다"는 검증이 아니다.
- 매체별 검증 명령을 실행하고 결과를 사용자에게 보여준다.
