# Pre-production — 코드 전에 확정하는 3문서

세 문서를 **절대 한 파일로 합치지 않는다.** 목적(왜), 구조(무엇), 스타일(어떻게)이 한 컨텍스트에
섞이면 LLM이 셋을 뒤섞어 평균값을 낸다 — 그게 "AI 티"의 구조적 원인이다.

```
기획서 (Project Summary)   왜 존재하는가 · 범위 · 하지 않을 것
      ↓
UX 설계 (UX Flow)          시나리오 · 데이터 스키마 · 컴포넌트 목록
      ↓
비주얼 디렉션 (Visual Direction)  토큰 · 타이포 · 색 · 이미지 파이프라인 · 모션
```

## 순서와 작성 주체

1. **Ideation (사람 + 대화형 모델)** — 브랜드 세계관 한 문장을 뽑는다. 예: "하루 빛의 흐름을
   보여주는 건축 조명 브랜드". 이 한 문장이 이후 모든 결정의 필터가 된다.
2. **기획서** — 그 문장을 목적·범위·금지사항으로 구체화한다.
3. **UX 설계** — 데이터 규격과 컴포넌트 목록을 **비주얼 없이** 확정한다. 시각 디자인이 없어도
   스키마와 컴포넌트 이름은 정할 수 있다.
4. **비주얼 디렉션** — 숫자로 확정한다. 색온도, hex, 폰트, 간격 스케일, 모션 duration/easing.

> 순서를 바꾸면 안 된다. 비주얼을 먼저 정하면 데이터가 비주얼에 맞춰 잘리고, 기획을 먼저 확정하지
> 않으면 섹션을 나중에 덧붙이게 되면서 스토리텔링이 끊긴다.

## ① 기획서 (Project Summary)

역할: 사이트/산출물의 **존재 목적과 다룰 범위**.

반드시 포함:

- **한 문장 정의** — "단순 스펙 나열이 아니라, 시간과 공간 속의 빛 상태로 제품을 경험하게 하는
  온라인 쇼케이스" 처럼. 기능 목록이 아니라 경험으로 쓴다.
- **대상 사용자** — 누가, 어떤 상황에서, 무엇을 얻고 떠나는가.
- **범위(In scope)** — 다룰 페이지·섹션·산출물.
- **하지 않을 것(Negative constraint)** — 가장 중요하고 가장 자주 빠진다. 예: "가격 비교 없음",
  "장바구니 없음", "형광색·순수 검정 배경 금지", "3D 뷰어 없음". 금지 목록이 없으면 결과물은
  세상 모든 평균 사이트가 된다.
- **성공 기준** — 이 산출물이 잘 됐다는 걸 무엇으로 판단하는가.

템플릿: `assets/project-summary.template.md`.

## ② UX 설계 (UX Flow)

역할: 추상적 개념을 **시나리오 + 데이터 스키마 + 컴포넌트 목록** 으로 구체화.

반드시 포함:

- **사용자 시나리오** — "방문 → 히어로에서 브랜드 무드 인지 → 제품 그리드 탐색 → 카드 클릭 →
  상세에서 스펙·설치 방식 확인 → 문의". 각 단계마다 무엇을 보여줄지.
- **데이터 스키마** — 엔티티별 필드와 타입. 시각 디자인이 없어도 확정 가능하다.
  예: `product: { id, name, type, installMethod, lightTemp(K), imageDay, imageNight, specs{} }`
- **컴포넌트 목록** — 필요한 UI 단위를 이름으로 나열: `LineGrid`, `ProductCard`, `ProductGrid`,
  `BrandMoodPano`, `TimelineBar`, `SpecTable`, `InquiryForm`.
- **상태 정의** — 앱이면 로딩/빈/에러/권한없음/오프라인 상태를 여기서 정한다(정적 쇼케이스면 생략
  가능하지만, 생략했다는 사실을 명시).
- **데이터 위계(Hierarchy)** — 텍스트의 위계가 레이아웃 구조를 결정한다는 원칙을 여기서 못박는다.
  "제품명(1) > 유형(2) > 스펙(3)" 처럼 위계를 정하면 레이아웃이 따라 나온다.

템플릿: `assets/ux-flow.template.md`.

## ③ 비주얼 디렉션 (Visual Direction)

역할: **디자인 토큰 + 이미지 생성 파이프라인** 정의. 이 문서가 실제로 가장 자주 열린다.

반드시 포함:

- **톤 한 단어 + 그 톤의 반대말** — "따뜻한 건축적 미니멀" vs "차가운 테크 미니멀".
- **색 토큰** — 배경(warm background), 텍스트(warm black), 악센트, 상태색. hex 를 명시한다.
  순수 `#000`/`#fff` 대신 웜톤 검정(`#1A1714` 계열) 등을 의도적으로 고른다.
- **색온도·재질 같은 물리 파라미터** — 예: "빛 색온도 3800K", "무광 검정 알루미늄",
  "화이트 프로스티드 글래스". 이미지 프롬프트와 CSS가 같은 값을 공유한다.
- **타이포 스케일** — 폰트 패밀리(디스플레이/본문), 크기 스케일(clamp 포함), 행간, 자간, 무게.
- **간격 스케일** — 4 또는 8 기반.
- **반경·그림자·테두리** — AI 티 방지에 중요하다. "둥근 카드 + 큰 그림자" 기본값 금지.
- **모션** — duration/easing 세트, 등장 순서, 어떤 패턴을 쓸지(용어로).
- **이미지 파이프라인** — 고정 키워드(A)와 가변 키워드(B) 분리, 세트 규칙(낮/밤 등), 구도·여백 규칙,
  배경색과 웹 배경 토큰을 일치시켜 경계면을 없애는 규칙.
- **금지 목록** — 사용하지 않을 폰트, 색, 효과.

템플릿: `assets/visual-direction.template.md`, 토큰 CSS: `assets/design-tokens.template.css`.

## 이미지 프롬프트 A+B 구조

20개 제품을 한 세트로 보이게 하는 핵심은 **고정부와 가변부 분리**다.

```
A (고정, 모든 이미지 동일)
  "matte black anodized aluminum and white frosted glass,
   front elevation view, centered, generous negative space,
   seamless {BACKGROUND_TOKEN} background, soft directional studio light {K}K,
   no props, no text, no logo, product photography, 85mm, f/8"

B (가변, 제품별)
  "slim linear pendant, 1200mm, warm 3800K light bar, low profile canopy"
```

- 배경 토큰을 CSS 배경 토큰과 **같은 문자열**로 쓴다 → 이미지 경계선이 사라진다.
- 세트 규칙: 낮(12시) / 밤(20시) 2컷, 또는 4단계(12/16/20시) 블렌딩용 4컷.
- 배치 규칙(중앙 정렬, 여백 비율)을 A에 못박아야 그리드에서 리듬이 생긴다.
- 템플릿: `assets/image-prompt.template.md`.

## 사례 (영상 원본)

- 컨셉: "하루 빛의 흐름을 보여주는 건축 조명 브랜드, Lumenstate"
- 20개 제품 × 낮/밤 = 40컷을 A+B 프롬프트로 생성.
- 자체 스타터킷(Line Grid 컴포넌트, Storybook 세팅, Taxonomy MD)이 이미 있어서 1시간 조립이 가능했다.
  **스타터킷 없이는 그 시간이 나오지 않는다** — 사용자에게 이 전제를 정직하게 말한다.
